# mock-anthropic

A local server that stands in for every network host Claude Code talks to, so that programs which run Claude Code can be tested with no Anthropic login, no subscription, and no network access, and get the same result on every run.

It is the one shared mock for all of our projects. It replaces the copy in `brandon-fryslie/claude-code-edu-workshop` under `tools/mock-api`.

## Goals

1. A test that runs a real Claude Code binary against the mock needs no credentials, no subscription, no quota, and no network connection, and it passes or fails the same way on every run.
2. Every response is either generated by code from the request and a small declared input, or replayed from a recording of real traffic.
3. Anything the mock cannot answer fails loudly and names the request, so a gap is never silent.
4. One mock, reused by every project, and not tied to any one Claude Code version.
5. Any Claude Code instance can be pointed at the mock. Using it never requires the mock to launch Claude Code.

## Hosts covered

- `api.anthropic.com`: Messages, token counting, OAuth account endpoints, CLI bootstrap, feature flags, event logging, MCP server lists, and the rest of what Claude Code calls at startup and during a session.
- `platform.claude.com`: the OAuth token endpoint.
- `claude.ai`
- `downloads.claude.ai`: the plugin marketplace version pointer.
- `raw.githubusercontent.com`: the Claude Code changelog.
- `http-intake.logs.us5.datadoghq.com`: the log intake.
- `browser-intake-us5-datadoghq.com`: error tracking.
- `mcp-proxy.anthropic.com`: claude.ai connector traffic, refused as out of scope.

## How a program reaches it

The mock listens on `127.0.0.1` on one port and accepts requests in two ways:

- **As an HTTPS forward proxy.** The program under test sets `HTTPS_PROXY` (and the other proxy variables Claude Code reads) to the mock, and `NODE_EXTRA_CA_CERTS` to the mock's CA certificate. The mock answers `CONNECT` to port 443 of every known host with a certificate signed by its own CA. The CA and the leaf certificate are generated with `openssl` on first start. A `CONNECT` to a host the mock does not know, or to any other port, is refused with a 403 that names it.
- **As a plain origin.** A request sent straight to the mock's port (for example, from a proxy the program puts in front of Claude Code with the mock as its upstream) is answered as if it had been addressed to `api.anthropic.com`. A connection whose first request names another host in its target (`GET http://example.com/`, as an `HTTP_PROXY` client sends every request) is refused with a 403 that names the host.

## Inputs

Each generated response is a function of the request and of two declared inputs. Replayed responses come from a third input, recordings.

### The account

The identity the mock logs Claude Code in as: account UUID, email, organization UUID, organization name, subscription type. It has a fixed default, and a consumer may override it. Every response that carries identity (OAuth profile, roles, bootstrap, organization-scoped paths) is derived from it. The default values are obviously synthetic (for example, `00000000-0000-4000-8000-000000000001`). No real account data appears anywhere in the repository.

### Scripts of model replies

A consumer supplies a directory of script files. Each file says which Messages requests it answers and what reply to generate.

- **Matching**: substrings that must appear anywhere in the raw request body, and substrings that must appear in the request's last `user` message. A `system`-role message in `messages` is not a `user` message, so its text is matched only through the raw body. No conditions means every Messages request.
- **Reply**: a list of content blocks (`text`, `tool_use` with a name and input, `thinking`) and a stop reason (`end_turn`, `tool_use`, `max_tokens`), optionally with a delay between streamed events. Alternatively, a literal status, headers, and body for testing error handling (a 429, a 500, an overloaded error).
- **Order**: scripts are tried in a defined order (file name order within a directory, consumer directories ahead of the mock's built-in ones). The first match answers.
- **Reloading**: script directories are read as each request is answered, so a test can write a script after the mock has started. A script is a file whose name ends `.json` and does not start with `.`, so a test that writes it under another name and renames it into place never has it read half-written.
- **A bad script**: a script that cannot be read or is not a valid script fails every Messages request, matched or not, with a 500 and a `FAILED` line that names its path.

`serve --scenarios DIR` adds a consumer directory. The flag may be repeated.

### Recordings

The mock is a record/replay request server. In record mode it forwards each request to the real host, using the recording user's real login, and saves the exchange. In replay mode it answers matching requests from saved exchanges.

- **Scrubbing**: before an exchange is saved, each of these kinds is replaced, in the request and the reply, wherever it appears in the decoded JSON (keys, values, and a JSON object carried inside a string such as `metadata.user_id`): every credential the request carried, and anything shaped like one (`sk-ant-` keys, JWTs, bearer tokens), with the mock's token; every email address, with the account input's; the account UUID that `metadata.user_id` marks (`_account_<uuid>`, or `account_uuid`), with the account input's; every other UUID, the organization's included, since the text does not say which is which, with a synthetic UUID that depends only on the UUID it replaces; and the per-user hash in `metadata.user_id`, with a fixed one. The scrubbed exchange is then scanned for each kind, and an exchange with any left is not saved. Other text in the conversation (paths, host names, names, system prompts) is saved as it is: the consumer reviews a recording before committing it.
- **Format**: one file per exchange, `NNNN.json`, holding `{version, request, reply, message_id}`: the scrubbed request body as sent, the assistant message it was answered with (its content blocks and stop reason, in a script file's `message` reply form, whether it arrived as a stream or as JSON), and that message's id. Only successful `POST /v1/messages` exchanges are saved, other than Claude Code's own model calls, which are answered by built-ins. Headers are never saved.
- **Location**: recordings belong to the consumer and live beside its tests. This repository holds none.
- **Matching**: a replayed Messages request matches a recorded one by its key: where it sits in the conversation, the text of its prompt, and its tool results. Claude Code names the reply a request continues in `diagnostics.previous_message_id` (null for the first request of a conversation), whether or not the account's flags make it send a `thread` object, and with `thread` on it sends only the new turn in `messages`; so the position is that id, never the number of messages, and a request without it has no key and matches no recording. The prompt is the last text block of the last `user` message that is not a `<system-reminder>`; a tool result is its text with `<system-reminder>` spans removed, and whether it is an error; the `tool_use` ids are not part of it. Nothing else of the request is read: the system prompt, `system`-role messages, session IDs, timestamps, metadata, model, `max_tokens`, `thinking`, tools and the rest differ between runs and between Claude Code versions. (Measured on 2.1.289, 2.1.296 and 2.1.299.) Before it is compared, a live request is scrubbed as a recording is, so that text holding an email, a UUID or a token matches its own recording; this is why replay's `--account` must be the one the recording was made with, and why a credential in a prompt that does not look like a token, replaced only when recorded, would not match. The first recording, in numbered order, with a key answers it; later ones with the same key are reported at startup as shadowed. The reply is the recorded one with the id of the real reply, so the request that continues it names an id the recording holds.
- **Loading**: `serve --recordings DIR` reads every recording once, at the start, and refuses to start if one cannot be read or its request has no key, naming its file. Scripts, by contrast, are read as each request is answered: a test writes a script while the mock runs, and a recording is captured traffic. Recordings are tried after the consumer's scripts and before the built-in answers. Every Messages request is scrubbed to be keyed, with or without recordings; one the scrub cannot make clean fails with a 500 and a `FAILED` line.
- **Scope**: replay answers the conversations under test. The startup and account endpoints (OAuth, bootstrap, feature flags, telemetry, and the rest) are answered by generators, not by recordings.

## What the mock generates

### Messages (`POST /v1/messages`)

- If the request asks for a stream, the reply is real server-sent events in the order the API sends them: `message_start`, `content_block_start`, the deltas (`text_delta`, `input_json_delta`, `thinking_delta`), `content_block_stop`, `message_delta` with the stop reason and usage, `message_stop`. Otherwise the reply is one JSON message.
- Message IDs and `tool_use` IDs are generated, unique within a run, and deterministic given the request. A replayed reply keeps the id of the reply it was recorded from, so it is unique within a run only while its recording is replayed once.
- Usage numbers are present and plausible.

### Claude Code's own model calls

Claude Code makes some model calls beside a turn. The mock recognizes each one by its prompt and generates the answer, so a consumer never has to script them:

- **Session title.** Both phrasings are covered: "Generate a concise, sentence-case title" and "You are naming a coding session so the user can pick it out of a long list of sessions." Both ask, through the request's output format, for a JSON object with one string field, `title`; the answer is that object.
- **Auto mode permission classifier.** Its system prompt opens with "You are a security monitor for autonomous AI coding agents." The answer is in the format the prompt asks for: `<severity>N</severity>`, where a value below 50 allows the action; `<block>yes</block>` / `<block>no</block>`; or a `classify_result` tool call (the `tengu_auto_mode_config` flag's `twoStageClassifier` selects among them). The default allows; a consumer can script a block.
- **Quota probe.** A request for one token (`max_tokens: 1`) whose last user message is exactly `quota`. Claude Code reads only the rate-limit headers; the answer is a one-token message cut off at `max_tokens`.

A consumer script that matches one of these requests takes precedence over the built-in answer.

### Every other in-scope endpoint

Each one has a generator that produces a minimal valid response, derived from the account. The current list:

- OAuth profile, roles, usage, validate, and token
- CLI bootstrap
- Feature-flag eval (`/api/eval/{client_key}`)
- Event logging, batch and v2 batch
- `metrics_enabled`, remote managed settings, policy limits
- `penguin_mode`, grove config, referral eligibility, overage credit grant
- The MCP registry and MCP server list
- The plugin marketplace version pointer
- The changelog
- Token counting
- `GET api.anthropic.com/api/oauth/organizations/{org}/skills/list-skills`
- `GET api.anthropic.com/api/organizations/{org}/model_selector/cc`
- `GET api.anthropic.com/api/oauth/organizations/{org}/marketplaces`
- `GET api.anthropic.com/api/oauth/organizations/{org}/plugins/list-plugins`
- `POST http-intake.logs.us5.datadoghq.com/api/v2/logs`: the Datadog log intake
- `POST browser-intake-us5-datadoghq.com/api/v2/logs`: Datadog error tracking

### Endpoint table

A single table lists every endpoint Claude Code is known to call: host, method, path template (`{name}` in a path segment matches any non-empty text there, so `{org}` matches one whole segment and `{sha}.zip` one that ends in `.zip`), and either the generator that answers it or the reason it is out of scope. Out-of-scope endpoints (remote sessions, the browser login flow, feedback upload, and so on) are refused with their reason.

A `coverage` command lists every endpoint as answered or out of scope, and exits non-zero if an in-scope endpoint has no generator.

## Failure behavior

- A request with no endpoint, an out-of-scope endpoint, or a Messages request that no script and no built-in matches gets a 400. The body names the method, host, path, and why. The mock also writes one `UNMATCHED` line on stderr.
- A refused `CONNECT` writes a `REFUSED` line on stderr. So does a plain connection whose first request is addressed to another host, and a connection that does not open with an HTTP request line, such as TLS sent straight to the port.
- A failure of the mock's own writes a `FAILED` line: a generator that throws (the client gets a 500), a response body that breaks partway, or a connection that closes before any request reaches the mock (for a tunnel, most often a client that does not trust the CA).
- Every request and every connection writes exactly one line, starting with its outcome: `SERVED`, `UNMATCHED`, `FAILED` or `ABORTED` for a request, `CLOSED`, `REFUSED` or `FAILED` for a connection. Each message Go's HTTP server logs about the mock's own handling, such as a panic it caught, is a mock bug and writes one `FAILED` line too, its record naming the event `server` and carrying the logged text as `message`.
- A consumer test can therefore fail on any `UNMATCHED`, `REFUSED` or `FAILED` line, and should.

## Commands

The mock is a single Go binary: `mock-anthropic <command> [args]`. Exit codes: 0 success, 1 the answer is "no" (for example, coverage has gaps) or the mock failed, 2 a wrong command line.

Every invocation ends with one line on stderr recording it, in the same form as the request and connection lines: `OK`, `NO`, `USAGE` or `FAILED`, then the record as JSON, with the arguments, the exit code, what first asked it to end (`ended_by`: the signal, `crash` for an error the mock did not catch, or `null` when the command finished by itself), and what the command learned (for `serve`: its port, the CA path, the account file or `null` for the default, the script directories, and whether each certificate was generated or reused; for `login`: the config directory and whether it made it, the account file or `null`, the trusted project paths, whether each file was created, replaced or removed, and how many keychain entries it removed, or `null` where Claude Code uses no keychain; for `env`: the port, the CA path, the config directory, and the names of the variables it printed). An error the mock did not catch ends the invocation as `FAILED`.

- `serve [--port N] [--scenarios DIR]... [--recordings DIR]... [--account FILE]`: start the mock. `--recordings` adds a directory of recordings to answer from (see "Recordings"); the invocation record learns the directories and the shadowed files. Every Messages answer's record carries `key`: the key the request was compared by (its thread, the start of its prompt, a digest of it and of each tool result), or `none:` and why, and for a recording's answer `recording`: the file. Port 0 picks a free port. `--account` replaces the default account with the one in FILE. Once listening, it prints exactly one JSON line on stdout, `{"port": N, "ca": "<path to CA certificate>"}`, and writes human-readable logs on stderr. It runs until SIGINT, SIGTERM or SIGHUP, then closes every connection and exits 0; a second signal while it is closing ends it at once, as `FAILED`.
- `login <config-dir> [--trust <project-dir>]... [--account FILE]`: write a Claude Code config directory that the mock accepts as logged in. It holds an OAuth credentials file with the mock's token and scopes, the account, completed onboarding, the official plugin marketplace recorded as already installed (`officialMarketplaceAutoInstallAttempted` and `officialMarketplaceAutoInstalled`, both true, so Claude Code does not download it on first start, read from 2.1.299; the config states an install that never happened), and the given projects marked trusted, each under its real path. `--account` is as for `serve`. This is the one place that defines what a mock login looks like; consumers call it instead of writing those files themselves. A login into a directory that already holds one replaces both files whole and removes what Claude Code would read ahead of them: a legacy `.config.json` in the directory, and on macOS the keychain entry Claude Code keeps for that directory. The consumer sets `CLAUDE_CONFIG_DIR` to exactly the path `login` records, because Claude Code names that keychain entry after the string, and leaves `CLAUDE_SECURESTORAGE_CONFIG_DIR` unset: Claude Code reads both the keychain entry and the credentials file from the directory it names instead.
- `env --port N --ca FILE --config-dir DIR`: print, one `NAME=value` per line, the environment variables that point a Claude Code instance at a running mock: `HTTPS_PROXY` and `HTTP_PROXY` in upper and lower case, all `http://127.0.0.1:N`; `NODE_EXTRA_CA_CERTS`; and `CLAUDE_CONFIG_DIR`. A shell reads the output back to exactly these values: a value with a character a shell treats specially is single-quoted. `--ca` must name an existing file and `--config-dir` is made absolute. The mock does not launch the instance and cannot unset anything in it, so the consumer must leave these unset in that instance, because each routes around the mock or replaces its login (read from Claude Code 2.1.289): `ALL_PROXY`, `NO_PROXY`, `ANTHROPIC_UNIX_SOCKET`, `CLAUDE_CODE_PROXY_RESOLVES_HOSTS`, `CLAUDE_CODE_ENABLE_PROXY_AUTH_HELPER`; the TLS overrides `NODE_TLS_REJECT_UNAUTHORIZED`, `CLAUDE_CODE_CERT_STORE`, `CLAUDE_CODE_CLIENT_CERT`, `CLAUDE_CODE_CLIENT_KEY`, `CLAUDE_CODE_CLIENT_KEY_PASSPHRASE`; every endpoint override (`ANTHROPIC_BASE_URL`, every other `*_BASE_URL` and provider endpoint, `CLAUDE_CODE_API_BASE_URL`, `CLAUDE_CODE_CUSTOM_OAUTH_URL`, `CLAUDE_CODE_GB_BASE_URL`, `USE_LOCAL_OAUTH`, `USE_STAGING_OAUTH`, `CLAUDE_LOCAL_OAUTH_*_BASE`, `CLAUDE_BRIDGE_BASE_URL`, `CLAUDE_BRIDGE_SESSION_INGRESS_URL`, `CLAUDE_REMOTE_TOOLS_BRIDGE_URL`); the provider switches `CLAUDE_CODE_USE_BEDROCK`, `_VERTEX`, `_FOUNDRY` and the other `CLAUDE_CODE_USE_*` that name a provider; every credential and sign-in source (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`, `ANTHROPIC_CUSTOM_HEADERS`, `ANTHROPIC_PROFILE`, `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `AWS_BEARER_TOKEN_BEDROCK`, the `*_FILE_DESCRIPTOR` auth variables, `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`, `CLAUDE_CODE_HOST_AUTH_ENV_VAR`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`); and the settings sources `CLAUDE_CODE_REMOTE_SETTINGS_PATH` and `CLAUDE_CODE_MANAGED_SETTINGS_PATH`. An Anthropic profile outranks the stored login, and Claude Code looks for one in `ANTHROPIC_CONFIG_DIR`, else `$XDG_CONFIG_HOME/anthropic`, else `~/.config/anthropic`; `env` does not print `ANTHROPIC_CONFIG_DIR`, so a consumer on a machine that holds such a profile sets it to an empty directory.
- `record --dir DIR [--port N] [--account FILE]`: as `serve`, but each request is forwarded to the real host with the client's own login (and no proxy, whatever `HTTPS_PROXY` says), and the Messages exchanges that succeed are scrubbed and saved into DIR, which must exist, as the next unused `NNNN.json`. The client's response is the upstream's, whatever happens to the recording. Each request's record carries `recording`: `file` and the count scrubbed of each kind, or `skipped` or `refused` or `failed` with why. The invocation record learns the port, the CA path, the directory, the account file and the certificates at the start, and at the end how many exchanges were `saved`, `skipped`, `refused` (unreadable or not scrubbable) and `failed` (upstream unreachable or cut short); it answers `NO` if any were refused or failed.
- `coverage`: as described under Endpoint table.

## Consumers

- **cc-hands** (`promptctl/cc-hands`). Its pytest end-to-end tests run the hands brain: the pinned Claude Code 2.1.289, interactive in a terminal, behind hands' own proxy. The mock is that proxy's upstream, and it is `HTTPS_PROXY` for every other host. The tests write scripts per test and fail on any unmatched request. Its CI runs on `macos-14` and fetches the mock at a pinned tag with no secret.
- **claude-code-edu-workshop**. Its `tools/mock-api` is replaced by this project.

## Technology

- Go.
- `go test ./...` runs the tests, and `go vet ./...` checks the code.
- CI (GitHub Actions) runs the tests and `go vet` on every pull request.
- Releases are git tags, and consumers pin a tag.
- The repository is public, so nothing in it identifies a real account.

## Acceptance

- `go test` and `go vet` pass in CI.
- `coverage` exits 0.
- Claude Code pointed at a running `serve` and logged in with `login`, run as `claude -p "Say hello and nothing else." --output-format text`, prints the scripted reply, exits 0, and the mock logs no `UNMATCHED` or `REFUSED` lines.
- An interactive Claude Code session runs a scripted tool call (`Bash`) through the auto mode classifier and then a scripted text reply, with no `UNMATCHED` or `REFUSED` lines.
- The repository contains no real identifiers. A test enforces this by scanning the tree for UUIDs other than the declared synthetic ones.
- cc-hands' end-to-end tests pass against a tagged release.
